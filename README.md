# Проект: Классификация обращений службы технической поддержки

**Датасет:** https://huggingface.co/datasets/Tobi-Bueck/customer-support-tickets

**Цель проекта:** разработать систему автоматической маршрутизации обращений пользователей в соответствующую очередь службы технической поддержки на основе содержания обращения.

## 1. Разведочный анализ и подготовка данных

### 1.1. Исследование структуры датасета

- Изучить доступные признаки и их типы.
- Определить целевую переменную `Queue`.
- Исследовать поля `Subject` и `Body` как основные источники информации для классификации.
- Проанализировать дополнительные признаки: `Type`, `Priority`, `Language`, `Tags`.

### 1.2. Анализ качества данных

- Проверить наличие пропущенных значений.
- Найти полные и частичные дубликаты обращений.
- Исследовать длину заголовков и текстов обращений.
- Проанализировать языковой состав данных.
- Проверить наличие аномальных и некорректных текстов.

### 1.3. Анализ целевой переменной

- Определить количество классов `Queue`.
- Построить распределение количества обращений между очередями.
- Оценить степень дисбаланса классов.
- Найти классы с небольшим количеством примеров.
- Исследовать похожие по смыслу очереди, между которыми модель потенциально может ошибаться.

### 1.4. Подготовка данных

- Объединить `Subject` и `Body` в единый текст обращения.
- Выполнить минимальную очистку текста.
- Закодировать целевую переменную.
- Разделить данные на `train / validation / test` с сохранением распределения классов.

**Результат этапа:** подготовленный датасет и понимание основных особенностей задачи классификации.

## 2. Построение baseline-моделей

Цель этапа — получить простое решение, относительно которого будут оцениваться все последующие улучшения.

### 2.1. Простейший baseline

- Предсказывать наиболее популярный класс.
- Рассчитать метрики baseline-модели.

### 2.2. Классические методы машинного обучения

Преобразовать текст при помощи:

- Bag of Words;
- TF-IDF.

Обучить и сравнить несколько моделей:

- Logistic Regression;
- Linear SVM;
- Naive Bayes.

### 2.3. Оценка моделей

Использовать:

- Accuracy;
- Macro F1;
- Weighted F1;
- Precision / Recall по отдельным классам;
- Confusion Matrix.

Основной метрикой использовать **Macro F1**, поскольку классы могут быть распределены неравномерно.

**Результат этапа:** baseline-модель классификации обращений и базовый уровень качества.

## 3. Анализ ошибок baseline-модели

Провести детальное исследование случаев, в которых модель ошибается.

### 3.1. Анализ матрицы ошибок

Определить:

- какие очереди модель чаще всего путает;
- какие классы определяются лучше и хуже;
- связано ли качество классификации с количеством примеров класса.

### 3.2. Анализ отдельных обращений

Рассмотреть примеры:

- правильных предсказаний;
- неправильных предсказаний;
- предсказаний с низкой уверенностью.

Попытаться определить причины ошибок:

- слишком короткий текст;
- неоднозначное обращение;
- несколько проблем в одном обращении;
- близкие по смыслу очереди;
- редкие классы.

**Результат этапа:** понимание ограничений baseline-модели и направлений дальнейшего улучшения.

## 4. Разработка ML-сервиса

### 4.1. Backend

Реализовать API на FastAPI.

Основной endpoint:

```text
POST /predict
```

Пример входа:

```json
{
  "subject": "Cannot connect to VPN",
  "body": "After updating my laptop I cannot connect to the corporate VPN..."
}
```

Пример ответа:

```json
{
  "queue": "Technical Support",
  "confidence": 0.87,
  "alternatives": [
    ["IT Support", 0.08],
    ["Product Support", 0.03]
  ]
}
```

### 4.2. Telegram-бот

Реализовать пользовательский интерфейс:

```text
Пользователь
      ↓
Telegram Bot
      ↓
FastAPI
      ↓
ML-модель
      ↓
Technical Support — 87%
```

Пользователь отправляет обращение, после чего бот показывает:

- рекомендуемую очередь;
- уверенность модели;
- альтернативные варианты.

### 4.3. Контейнеризация

Подготовить:

- Dockerfile;
- конфигурацию приложения;
- сохранение и загрузку обученной модели.

## 5. Улучшение классической ML-модели

Исследовать влияние различных способов обработки и представления текста.

### 5.1. Улучшение TF-IDF

Проверить:

- word n-grams;
- character n-grams;
- различные значения `min_df` и `max_df`;
- ограничение размера словаря;
- обработку `Subject` и `Body` отдельно.

Отдельно проверить гипотезу:

> Дает ли заголовок обращения дополнительную информацию для определения очереди по сравнению с использованием только основного текста?

### 5.2. Работа с дисбалансом

Исследовать:

- `class_weight="balanced"`;
- различные способы взвешивания классов;
- влияние редких классов на Macro F1.

### 5.3. Использование дополнительных признаков

Проверить, улучшают ли качество классификации:

- язык обращения;
- тип обращения;
- приоритет;
- длина текста.

При этом отдельно оценить, какие признаки реально будут известны системе **до маршрутизации обращения**, чтобы избежать утечки целевой информации.

### 5.4. Подбор гиперпараметров

Выполнить подбор параметров для наиболее перспективных моделей с помощью:

- GridSearchCV;
- RandomizedSearchCV;
- Optuna.

**Результат этапа:** улучшенная классическая модель и экспериментальное исследование факторов, влияющих на качество классификации.

## 6. Применение нейронных сетей

### 6.1. Получение векторных представлений текста

Использовать предобученную модель для получения embeddings обращений, например Sentence Transformers.

Сравнить:

```text
TF-IDF -> классификатор
```

и

```text
Transformer embeddings -> классификатор
```

### 6.2. Fine-tuning Transformer

Обучить Transformer-модель непосредственно для многоклассовой классификации обращений.

Возможные модели:

- DistilBERT;
- BERT;
- RoBERTa;
- multilingual BERT / XLM-RoBERTa — если необходимо одновременно обрабатывать несколько языков.

На вход модели подавать:

```text
Subject + Body
```

На выходе получать вероятности принадлежности обращения к каждой очереди.

### 6.3. Сравнение подходов

Сравнить:

| Подход | Macro F1 | Weighted F1 | Скорость | Размер модели |
|---|---:|---:|---:|---:|
| TF-IDF + Logistic Regression | | | | |
| TF-IDF + SVM | | | | |
| Embeddings + классификатор | | | | |
| Fine-tuned Transformer | | | | |

Исследовать компромисс между качеством модели и вычислительной сложностью.

**Результат этапа:** нейросетевая модель и экспериментальное сравнение классических и современных NLP-подходов.

## 7. Механизм уверенности модели

Для практической системы недостаточно просто выдавать класс.

Модель должна возвращать:

- рекомендуемую очередь;
- вероятность / confidence;
- несколько наиболее вероятных очередей.

Пример:

```text
Technical Support — 0.76
IT Support        — 0.14
Product Support   — 0.07
```

Исследовать возможность введения порога уверенности:

```text
confidence >= threshold
        ↓
автоматическая маршрутизация

confidence < threshold
        ↓
передача обращения оператору
```

Подобрать `threshold` экспериментально и оценить, какую долю обращений система может маршрутизировать автоматически при заданном уровне качества.

**Результат этапа:** механизм безопасной автоматической маршрутизации обращений.

## Итоговый результат проекта

В результате должна быть разработана полноценная система автоматической маршрутизации обращений:

```text
обращение пользователя
        ↓
NLP-модель
        ↓
определение очереди
        ↓
оценка уверенности
        ↓
автоматическая маршрутизация / передача оператору
```

Помимо работающего сервиса проект должен содержать экспериментальное сравнение нескольких методов классификации текста и исследование их применимости для автоматизации работы службы технической поддержки.

## Важное замечание

В качестве основных входных данных рекомендуется использовать:

```text
Subject + Body -> Queue
```

Не следует использовать `Answer` и другие признаки, которые появляются уже после обработки обращения, без отдельного обоснования, поскольку это может привести к утечке данных.
